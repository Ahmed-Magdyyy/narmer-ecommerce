# Notifications frontend contract

This document describes the implemented staff notification feed for B2C orders and B2B leads. The feed is a shared record of business events with a separate read receipt for each staff member. It is not a customer-facing notification API.

Related contracts: [shared API conventions](../../../../docs/frontend/api-conventions.md), [Orders](../orders/ORDERS_FRONTEND.md), and [Leads](../leads/LEADS_FRONTEND.md).

## Access and transport

The API is mounted under the store-specific staff dashboard. Use the current staff account's Bearer token for the selected store. The authenticated account must be active and have role `superAdmin`, `admin`, or `moderator` in that store. The API does not accept a user ID or store selector from the client; the mounted path and authenticated account determine both.

All endpoints return HTTP `200` and set `Cache-Control: no-store`. They use the shared success envelope: `success: true`, `code: "OK"`, localized `message`, `data`, and `requestId`. Errors use the shared error envelope with `success: false`, stable `code`, localized `message`, `errors`, and `requestId`, with no `data`. See [shared conventions](../../../../docs/frontend/api-conventions.md) for every envelope field and validation error entry. No notification endpoint requires a cookie, customer credential, or notification token.

| Header or setting | Required/default | Meaning and source |
| --- | --- | --- |
| `Authorization: Bearer <accessToken>` | Required | The selected store's current staff access JWT from Auth login/refresh. Refresh replaces this token. |
| `X-Language: en` or `ar` | Optional | Selects the returned title and envelope/error language. |
| `Accept-Language` | Optional fallback | Negotiates supported `en`/`ar` if no supported `X-Language` is supplied; otherwise configured `DEFAULT_LOCALE` applies, initially `en`. |
| `Accept: application/json` | Optional | These endpoints return JSON regardless; use the shared frontend JSON convention. |
| `Content-Type` | Not required for these bodyless calls | Do not send a body. If an unnecessary JSON body is sent, the shared parser still checks it before the handler. |
| `Origin` | Browser supplied | Browser CORS rules still apply. These Bearer-authenticated endpoints add no cookie-write Origin requirement. |
| Cookies / `credentials: 'include'` | Not used to select a viewer | Shared refresh calls require their own cookie transport; Notifications authorization uses only the Bearer JWT. |

Responses include the shared `X-Request-Id` and `Content-Language` headers. The request ID is generated by the server; retain it for reporting failed requests. Titles are plain text and must not be rendered as HTML.

The two route roots are:

| Store | Root |
| --- | --- |
| B2C | `/api/v1/admin/b2c/notifications` |
| B2B | `/api/v1/admin/b2b/notifications` |

There are exactly three operations under each root:

| Method and path | Purpose |
| --- | --- |
| `GET {root}` | List the authenticated staff member's feed, read state, and overall unread count. |
| `GET {root}/unread-count` | Read the overall unread count without loading feed items. |
| `PATCH {root}/:notificationId/read` | Mark one notification as read for the authenticated staff member and return its DTO. |

The complete mounted paths are:

| Method | B2C path | B2B path |
| --- | --- | --- |
| GET | `/api/v1/admin/b2c/notifications` | `/api/v1/admin/b2b/notifications` |
| GET | `/api/v1/admin/b2c/notifications/unread-count` | `/api/v1/admin/b2b/notifications/unread-count` |
| PATCH | `/api/v1/admin/b2c/notifications/:notificationId/read` | `/api/v1/admin/b2b/notifications/:notificationId/read` |

The response envelope and common transport errors follow [shared API conventions](../../../../docs/frontend/api-conventions.md). The examples below show the `data` value inside the standard success envelope.

## Feed event and visibility rules

The B2C feed receives one `order.placed` event for a real order. The B2B feed receives one `lead.submitted` event for a submitted lead. These events are written in the same MongoDB transaction as the business operation. A failure to enqueue the staff notification fails that business transaction. Replaying an already accepted submission or changing an order status or lead contact state does not create another arrival notification.

Every currently authorized staff member in a store sees that store's event feed. Read state is private to the current staff member. A staff member who joins later can see events already retained in the store feed; without earlier personal receipts, those events are unread. The system does not create per-recipient copies or backfill orders/leads created before this module was implemented. Each event is unique by store, event type, and resource ID. Current account/session/role checks apply on every request; blocking or soft-deleting an account removes access without deleting its previous read receipts.

Staff events do not require SMTP, a frontend tracking-link template, a Lead email address, or browser notification permission. The business transaction inserts the staff arrival record and any separately enabled customer email job together. Later SMTP failure does not change the staff feed or committed business resource.

The notification's resource contains only an `order` or `lead` identifier. It does not contain order details, lead contact data, an image, or a ready-made frontend URL. Choose the application's own frontend route and fetch `GET /api/v1/admin/b2c/orders/:orderId` for an order or `GET /api/v1/admin/b2b/leads/:leadId` for a lead, replacing the parameter with `resource.id`. Do not treat the resource ID as an authorization credential.

## `GET {root}`

### Query parameters

All query parameters are optional. Defaults apply when omitted.

| Name | Type and bounds | Default | Meaning and frontend behavior |
| --- | --- | --- | --- |
| `page` | Integer, 1–100000 | `1` | One-based page number. The server converts the validated string to an integer. |
| `limit` | Integer, 1–100 | `20` | Maximum number of returned items. The server converts the validated string to an integer. |
| `unreadOnly` | Exact string `true` or `false` | `false` | When `true`, returned items and pagination totals include only unread items. Other spellings or values fail validation. |

No query parameter chooses the user or store. The authenticated account and route root always do that. Unknown query names are ignored. Do not send `userId`, `store`, `null`, blank values, arrays, or unsupported spellings as substitutes for documented scalar values. GET calls have no body. No event-type, search, date or read-time filter exists.

### Response data

| Field | Type | Meaning |
| --- | --- | --- |
| `items` | Array of notification DTOs | The requested page, sorted by event time newest first, then by record ID descending for ties. It may be empty. |
| `unreadCount` | Integer, 0 or greater | Number of unread notifications across the entire store feed for this staff member. It is independent of `unreadOnly`, `page`, and `limit`. |
| `pagination` | Object, always present | Metadata for the requested page and current filter. |
| `pagination.page` | Integer | Effective page number. |
| `pagination.limit` | Integer | Effective page size. |
| `pagination.total` | Integer | Number of records matching the current `unreadOnly` filter, across all pages. |
| `pagination.pages` | Integer | `ceil(total / limit)`. It is `0` when `total` is `0`. |

Each `items[]` element has exactly this public shape:

| Field | Type / nullability | Meaning and source |
| --- | --- | --- |
| `id` | Lowercase 24-character hexadecimal string | Server-generated notification record ID, distinct from the business resource ID. Retain it to call the mark-read endpoint. |
| `type` | String enum | `order.placed` for B2C or `lead.submitted` for B2B. |
| `title` | String | Localized title selected using the shared request-language rules. No supported preference uses configured `DEFAULT_LOCALE`, initially `en`. |
| `resource` | Object | Identifier for the related business resource; it is not a detail payload or link. |
| `resource.type` | String enum | `order` for `order.placed`; `lead` for `lead.submitted`. |
| `resource.id` | Lowercase 24-character hexadecimal string | ID of the committed business Order or Lead, generated by that module. Retain it to open the protected resource detail. |
| `occurredAt` | ISO 8601 date-time string | Business event time stored when the event was first enqueued. It is not the time the feed was read. |
| `isRead` | Boolean | Whether this staff member has a read receipt for this notification. |
| `readAt` | ISO 8601 UTC date-time string or `null` | Server time of this staff member's first successful acknowledgment; `null` while unread. It does not change on retries. |

Every documented DTO field is always present. Only `readAt` is nullable; there are no optional or omitted item fields. `items`, counters and pagination come from current store records and the authenticated viewer's receipts. No store, user ID, internal creation/update timestamp or receipt ID is exposed.

Example B2C response data:

~~~json
{
  "items": [
    {
      "id": "671a10000000000000000001",
      "type": "order.placed",
      "title": "New order",
      "resource": {
        "type": "order",
        "id": "671a10000000000000000002"
      },
      "occurredAt": "2026-10-13T08:14:20.000Z",
      "isRead": false,
      "readAt": null
    }
  ],
  "unreadCount": 1,
  "pagination": {
    "page": 1,
    "limit": 20,
    "total": 1,
    "pages": 1
  }
}
~~~

Example B2B item title is `New request` in English and `طلب خدمة جديد` in Arabic. The B2C title is `New order` in English and `طلب جديد` in Arabic. The rest of the item shape is the same, with `type: "lead.submitted"` and `resource.type: "lead"` for B2B.

An empty store returns `items: []`, `unreadCount: 0`, and pagination `{ "page": 1, "limit": 20, "total": 0, "pages": 0 }`. With `unreadOnly=true`, a staff member who has read every event also receives an empty list and zero filtered total/count, although read events remain in the unfiltered feed. A requested page beyond `pagination.pages` returns an empty `items` array with the requested page number, retained total/pages and possibly a positive unread count from other pages. Do not treat that result as an empty store; return to page 1 or another valid page.

## `GET {root}/unread-count`

This request has no documented query parameters, path parameters or request body; extra query names are ignored. It does not load feed items. Its only data field is the required integer `unreadCount`, at least zero, computed for the current staff member across the selected store. Its data is:

~~~json
{
  "unreadCount": 3
}
~~~

The count belongs to the authenticated staff member and selected store. It covers every retained notification, regardless of page, current filter, or event type within that store.

## `PATCH {root}/:notificationId/read`

The path parameter `notificationId` is required and must be exactly 24 hexadecimal characters, from a returned notification `id`. Uppercase hexadecimal input is normalized to lowercase before lookup. Do not pass `resource.id`. There is no request body or documented query, and no client-supplied user, store, read time, or locale field. Extra query/body fields are ignored by this operation; malformed or oversized unnecessary JSON can still fail the shared parser. The current authentication and selected root determine the viewer and store; request headers determine the returned title.

On success, the data is the full notification DTO shown above, with `isRead: true` and `readAt` set to that staff member's first successful read time. Calling the endpoint again is safe: it returns the same viewer's receipt and preserves the original `readAt`. It does not mark the event read for other staff members and does not change the related order or lead.

This response has no `unreadCount` or pagination. Refetch the count/list; do not blindly subtract one on every acknowledgment because retries and concurrent tabs can acknowledge an already read event. Concurrent calls for the same account/event create one receipt and preserve its first timestamp. No `expectedVersion`, `expectedStatus`, idempotency key or transaction header is needed. A lost response can be retried with the same path. Marking read neither accepts an order nor marks a lead contacted. This single-record receipt write does not require a business transaction; Order/Lead event creation still requires its existing transaction.

Example response data:

~~~json
{
  "id": "671a10000000000000000001",
  "type": "lead.submitted",
  "title": "New request",
  "resource": {
    "type": "lead",
    "id": "671a10000000000000000003"
  },
  "occurredAt": "2026-10-13T08:14:20.000Z",
  "isRead": true,
  "readAt": "2026-10-13T08:19:02.000Z"
}
~~~

## Errors and recovery

| HTTP status | Code / condition | Frontend handling |
| --- | --- | --- |
| `401` | `UNAUTHORIZED` | Missing/expired/invalid/wrong-store Bearer token, invalidated session, or an inactive, blocked or deleted account. Refresh or reauthenticate through the existing Auth flow where appropriate; blocked/deleted accounts cannot regain access by retrying. |
| `403` | `FORBIDDEN` | The authenticated current account lacks an allowed staff role. Customer accounts cannot use this feed. |
| `403` | `EMAIL_NOT_VERIFIED` | Existing Auth checks require a confirmed email. Complete confirmation and sign in before accessing the dashboard. |
| `404` | `NOTIFICATION_NOT_FOUND` | The event ID is unknown in this store. Remove or refresh the stale feed item. |
| `422` | `VALIDATION_ERROR` | Correct the query values or provide a valid notification ID. Do not retry unchanged input. |
| `5xx` | Shared server or storage failure | Keep current UI state, show a retry option, and use bounded backoff. A read failure does not mean the event was deleted. |

Validation failures use the shared error envelope with field/location/code/message. Shared transport failures include 400 INVALID_JSON, 413 BODY_TOO_LARGE and 403 CORS_DENIED. Other-store and missing notification IDs both return 404 NOTIFICATION_NOT_FOUND. Only b2c/b2b roots are mounted; internal INVALID_STORE is not a normal frontend path. There is no extra Notifications-specific limiter, but API IP 240/minute and verified-account 120/minute limits apply. On 429 honor exposed Retry-After, pause polling and retain the feed; do not refresh tokens to evade account quotas. Infrastructure may supply its own limit/error. Unsupported routes follow shared 404 behavior. A saved acknowledgment remains saved if fetching the separate business resource fails; retry its authorized detail read separately.

## Suggested frontend flow and retained state

1. After staff authentication, load the feed for the active store with `page=1&limit=20`. Retain the selected store, current page and limit, current `unreadOnly` filter, each item’s `id` and `resource`, and the returned pagination values. Do not persist a staff user ID as a selector.
2. Show the `unreadCount` as the store notification badge for this staff member. It is a full-feed count, not the number of unread items on the current page.
3. When a staff member opens an unread item, call the matching store’s PATCH endpoint with its notification `id`. Replace the displayed DTO with the response and refresh the badge/list as needed. The operation is idempotent for that viewer.
4. Open the existing staff order or lead detail flow using `resource.type` and `resource.id`; then fetch its protected detail endpoint. Notification data does not grant access to that resource.
5. If polling is used, poll about every 30 seconds while the relevant staff view is visible, pause while the browser tab is hidden or the user is logged out, and back off on rate limits or failures. These are frontend polling recommendations; the server does not push notifications or guarantee an atomic snapshot across separate list and count requests.

List and count calls are independent reads. A new event or a concurrent read receipt can make their results differ between calls. Refetch when the UI needs a fresh count rather than assuming that a prior page response remains current.

Show loading separately from an empty feed. Keep previously loaded items on transient failures and show a retry action. Reset feed/cache state when logging out or changing accounts/stores; never reuse another viewer's read state. With unread-only filtering, remove a successfully acknowledged row and refresh the current page/count, returning to a valid page if totals shrink. On authorization failure, stop polling before attempting the shared Auth recovery flow.

## Retention and unavailable capabilities

The current models have no TTL expiry, delete endpoint, mark-all-read endpoint, or notification detail endpoint. A future retention or deletion policy is not specified here. There are no guest, customer, or public notification routes, no per-event status-change notifications, no recipient fan-out, and no notification email or push endpoint. Customer email delivery is a separate internal delivery mechanism; a notification API success does not report email delivery.

## Shared security and request throttling (2026-10-13)

Every endpoint in this contract participates in the API-wide effective-IP allowance of 240 requests per minute. Requests passing access-JWT authentication also participate in one store/account allowance of 120 requests per minute, shared across protected routes and sessions. Public login/refresh do not use this access-JWT allowance; guests have no stored account key. Earlier validation, IP or authentication failures may prevent later counters from being reached. Existing module limits are additional; see the complete [rate-limit table and response-header contract](../../../../docs/frontend/api-conventions.md).

Any endpoint can therefore return the shared 429 TOO_MANY_REQUESTS error, with no data and the normal success:false/code/message/errors/requestId fields. CORS exposes Retry-After (seconds), RateLimit and RateLimit-Policy to allowed browser origins. Preserve current form, IDs, versions, uploaded-file references and private credentials; pause polling/rapid requests and respect Retry-After. A 429 does not trigger token refresh. Resume using the module's documented safe read/replay rules, rather than assuming all mutations are idempotent. No request or response DTO field was added for limiting, and no limit header is a reusable credential.

These counters are local to the confirmed single Node.js process and reset on restart. Shared counters are required before adding workers/servers. This is application abuse protection; external network/HTTP DDoS filtering and verified proxy configuration remain deployment work. Read the [security report](../../../../docs/security.md) for actual proof and remaining acceptance limits.
